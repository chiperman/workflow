# 动态任务配置系统设计文档 (Dynamic Task System)

## 1. 需求背景

原有的系统采用了硬编码的方式实现保活任务（如固定的 GLaDOS 和 Supabase 服务类）。随着任务数量的增加，这种方式带来了以下问题：

- **维护成本高**：新增或修改任务必须修改代码并重新部署。
- **灵活性差**：无法通过 UI 界面快速开启/关闭某个任务或修改其配置。
- **扩展性不足**：无法支持通用的 HTTP 请求保活，每个新服务都需要写重复的类逻辑。

## 2. 解决方案：数据驱动架构

我们将系统重构为完全由数据库驱动的动态架构：

### 2.1 数据库层 (`keep_alive` 表)

表结构已扩展，现在包含以下核心字段：

- `service`: 唯一标识符（主键）。
- `name`: 显示名称。
- `description`: 任务描述（动态显示在卡片上）。
- `category`: 任务分类。
- `type`: 任务类型 (`http` 或 `supabase_internal`)。
- `config`: 存储 URL、Method、Headers、Body 的 JSON。
- `rules`: 存储成功判断标准（如状态码、JSON 路径匹配）的 JSON。
- `enabled`: 开关状态。

### 2.2 逻辑层 (`DynamicService` & `ServiceFactory`)

- **DynamicService**: 一个通用的执行类，能够解析数据库配置并发送 HTTP 请求，根据定义的 `rules` 自动判断执行结果。
- **ServiceFactory**: 负责根据服务 ID 从数据库加载配置并实例化对应的 `DynamicService`。

### 2.3 API 层

- `/api/tasks/[id]`: 统一的任务触发入口。
- `/api/service-config`: 任务的 CRUD 管理接口。
- `/api/cron-all`: 动态扫描所有启用任务并执行。
- `/api/health`: 动态报告所有任务的健康状态。

### 2.4 表现层 (UI)

- **动态渲染**: 首页卡片不再写死，而是根据 `useSystemHealth` 返回的列表自动生成。
- **配置弹窗 (`TaskConfigModal`)**: 提供可视化界面进行任务的新增、修改和保存。

## 4. 存在的问题与待办事项 (Current Issues)

1. **删除功能缺失**: 目前 UI 上的「删除任务」按钮仅有提示，尚未对接后端接口。
2. **校验规则 UI 过于原始**: 校验规则目前需要手动输入 JSON 字符串，建议后续改为表单化配置。
3. **环境变量兼容性**: 部分关键变量（如 GLaDOS Cookie）仍优先从系统环境变量读取，未来应考虑全面迁移至数据库加密存储。
4. **空数据状态**: 如果数据库中没有任务记录，首页缺乏明显的「快速开始」引导。

## 5. 数据库同步 (Database Setup)

所有任务元数据及配置均存储在数据库中。请务必在启动应用前执行 [**supabase/setup.sql**](../supabase/setup.sql) 以初始化最新的表结构与内置任务。
