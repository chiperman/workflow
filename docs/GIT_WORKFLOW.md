# Git 工作流交互规范

为了保证项目的开发效率与生产环境的稳定性，本项目采用以下 Git 工作流规范。

## 1. 分支职责说明

| 分支名称     | 职责定位                                                          | 合并限制                                                   |
| :----------- | :---------------------------------------------------------------- | :--------------------------------------------------------- |
| **`main`**   | **生产环境分支**。代表当前最稳定的生产版本。                      | 仅接受来自 `dev` 的合规合并。非紧急 Bug 修复禁止直接提交。 |
| **`dev`**    | **集成与测试分支**。用于各功能开发阶段的代码集成（Integration）。 | 接受 `feat` 或 `fix` 合并。代码必须先在 `dev` 验证。       |
| **`feat/*`** | **功能开发分支**。从 `dev` 拉出，完成后合回 `dev`。               | 短期存在，合并入 `dev` 后应当删除。                        |

## 2. 合并与提交规范

### 2.1 `feat` -> `dev` (功能集成)

- **提交方式**：通过 Pull Request (PR) 提交。
- **合并策略**：**Squash and Merge** (压缩合并)。
- **理由**：将开发过程中的琐碎 commit（如 fix typo, wip）合并为 1 个干净的语义化 commit，保持 `dev` 历史整洁。

### 2.2 `dev` -> `main` (正式发布)

- **提交方式**：通过 Pull Request (PR) 提交。
- **合并策略**：**Merge Commit** (普通合并)。
- **理由**：保留 `dev` 上的版本发布历史（包括 Tag 记录）并作为一个发布节点合入 `main`。

## 3. 自动发布流程 (CI/CD)

项目配置了 GitHub Actions 自动化发布：

1. **触发条件**：当有代码合并/推送至 `main` 分支时。
2. **自动化动作**：
   - 自动运行 `standard-version`。
   - 更新 `package.json` 版本号。
   - 自动生成 `CHANGELOG.md`。
   - 自动打出 **Git Tag**。
   - 自动创建 **GitHub Release**。
   - **自动回传**：工作流结束后，会自动将版本号和 Changelog 同步回 `dev` 分支，保持分支同步。

## 4. Commit Message 规范

推荐遵循 [Conventional Commits](https://www.conventionalcommits.org/) 规范，这直接影响 CHANGELOG 的生成：

- `feat: ...` -> 对应新功能
- `fix: ...` -> 对应缺陷修复
- `chore: ...` -> 对应构建过程或辅助工具的变动
- `docs: ...` -> 对应文档变更
